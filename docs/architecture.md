**从色块状态到三维动画：代码原理与阅读路线**

这份说明配合源码的逐行注释使用。阅读时可以先运行程序，再把一次按钮操作与下面的流程对应起来。

**一个色块怎样记录在程序里**

`model.py` 用长度为 54 的字符串记录六个面。面顺序固定为 `URFDLB`，每面 9 个字符，面内按正对该面的视角从上到下、从左到右排列。

颜色字符与面记号不要混淆：面记号 `B` 表示后面，颜色字符 `B` 表示蓝色；后面中心的颜色字符是 `G`。

| 面 | 字符串下标 | 复原时的颜色字符 |
| --- | --- | --- |
| U 顶面 | 0～8 | Y 黄色 |
| R 右面 | 9～17 | R 红色 |
| F 前面 | 18～26 | B 蓝色 |
| D 底面 | 27～35 | W 白色 |
| L 左面 | 36～44 | O 橙色 |
| B 后面 | 45～53 | G 绿色 |

每面的中心下标为 `4、13、22、31、40、49`。例如 `18` 是前面的左上色块，`22` 是前面中心。涂色只是改变一个字符，完成录入时才检查整个状态是否物理可复原。

magiccube 构造器使用另一种面顺序 `ULFRBD`。`library_cube()` 负责转换输入，`read_cube()` 负责转换输出。其他模块无需知道这个差异，这就是适配层的作用。

```python
# ---------- 仅用状态验证一个动作与逆动作 ----------
from rubik.model import CubeState  # 使用本项目的状态接口，不直接访问第三方内部数据。
cube = CubeState()  # 创建白底黄顶蓝前的复原状态。
cube.move('R')  # 右面顺时针转动 90 度。
cube.move("R'")  # 右面逆时针转动 90 度，抵消前一个动作。
print(cube.is_solved())  # 输出 True，说明两个动作相互抵消。
```

**为什么颜色数够了仍可能错误**

`validation.py` 先统计六色数量，再检查中心、角块和棱块。它使用贴片索引表读出每个块的颜色组合，并确认没有重复块或不存在的块。

角块可以在原位置有三种朝向，棱块可以有两种朝向。代码把角块扭转记录为 `0 / 1 / 2`，把棱块翻转记录为 `0 / 1`。合法状态要求棱翻转总数为偶数、角扭转总数是 3 的倍数，角与棱的位置排列具有相同奇偶性。

这里的“奇偶性”可以理解为把块重新排列到目标位置需要交换的次数是奇数还是偶数。代码用逆序对计算：排列 `[1, 0, 2]` 只有 `1` 在 `0` 前面这一个逆序对，因此是奇排列；`[0, 1, 2]` 没有逆序对，因此是偶排列。

正常面转动同时改变角与棱的位置，不能只交换两条棱而保持其他块完全不变。因此颜色数量正确仍不足以保证可复原。检查结果为 `None` 表示合法，否则为可显示给使用者的中文原因。

**求解器为什么不依赖打乱记录**

`solve_layer_by_layer(facelets)` 只收到当前的 54 个颜色。它先检查合法性，再在副本上运行 magiccube 的 `BasicSolver`。你手动录入的合法状态和程序生成的状态使用同一个求解入口。

`TeachingSolver` 扩展固定版本 1.2.0 的阶段方法，记录原始动作对应的教学阶段。这依赖第三方的内部阶段接口，因此升级 magiccube 时必须重新验收，不能仅修改依赖版本号。

算法为套用公式可能在内部旋转整块魔方。例如把原来的右面暂时当作前面。界面不能跟着强制改变用户视角，所以适配器使用另一个虚拟魔方跟踪参考朝向，用中心颜色识别真正需要转动的面。

最后把 `R2` 拆为两次 `R`，将每一步记录为不可变的 `SolutionStep(move, stage)`。输出前再用另一份模型从输入状态完整重放；只有确实复原才把动作列表交给播放器。

**层先法检查了哪些阶段**

| 阶段 | 完成标志 | 后续需要保持的部分 |
| --- | --- | --- |
| 白色十字 | 白色棱朝下，侧色与中心相同 | 底面十字 |
| 底层角块 | 整个底层复原 | 底层 |
| 中间层 | 四条中层棱复原 | 前两层 |
| 顶面十字 | 四条顶层棱的黄色朝上 | 前两层与顶面十字 |
| 顶层棱归位 | 棱的侧色对齐中心 | 已归位的棱 |
| 顶层角归位 | 顶层角块身份正确，允许朝向尚未正确 | 已完成的位置关系 |
| 顶层角转向 | 全部面恢复目标配色 | 完整复原 |

测试不仅检查最后的结果，还在阶段边界检查这些里程碑。这样能发现“最后虽然复原，但过程不符合层先法”的改动。

**三维坐标为什么有一次 z 轴取反**

模型采用 `x` 向右、`y` 向上、`z` 向前。小方块坐标只用 `-1 / 0 / 1`，例如 `(1, 1, 1)` 表示右、上、前的角块。法向量描述贴片朝向，前面法向量为 `(0, 0, 1)`。

显示引擎的前向约定与模型不同，`render_position()` 将模型 `(x, y, z)` 转为引擎 `(x, y, -z)`。只在这个边界转换，能让模型规则与显示约定分开。

`quarter_rotate()` 实现精确的四分之一圈转动。以绕 z 轴的正向 90° 为例，`(x, y, z)` 变成 `(-y, x, z)`，所以 `(1, 0, 0)` 转后是 `(0, 1, 0)`。

这来自二维旋转矩阵：`x' = x cosθ - y sinθ`，`y' = x sinθ + y cosθ`。代入 `θ = 90°`，`cosθ = 0`、`sinθ = 1`，就得到 `x' = -y`、`y' = x`。程序直接交换整数坐标并改变符号，避免浮点误差累计。

转动一个面时，该层色块的位置和法向量必须同时旋转。测试把几何变换得到的贴片置换与模型的实际转动对照，检查两者的方向是否一致。

**一次动画什么时候修改模型**

`view.py` 绘制 26 个主体与 54 个独立贴片。转动开始时，把选中一层的 9 个主体暂时挂到一个旋转父节点 `pivot`；每帧只改变这个节点的角度。

`playback.py` 接收时间增量，推进动画。只有完整达到 90° 后才调用一次 `cube.move()`，随后把几何恢复到标准网格，并根据新的颜色字符串同步画面。

这避免了“动画还只转了一半，模型已经提前变成下一步”的不一致。编辑和打乱被阻止进入正在播放的半步状态。

动画用 `3t² - 2t³` 平滑起停，其中 `t` 从 0 到 1。起点为 0，终点为 1；其导数 `6t - 6t²` 在两个端点都是 0，因此画面开始和停止时不会瞬间跳到最大速度。这里用于改变视觉角度的推进方式，不改变模型动作。

**速度、暂停与长按为什么放在一个播放器里**

默认相邻动作开始间隔是 1 秒，其中动画 0.3 秒、等待 0.7 秒。自动五倍把两段都除以 5，所以不是只让动画快、等待仍保持不变。

当前动作保存开始时的倍率，切换档位不会使半步突然跳变。下一动作读取最新档位。手动单击与长按始终使用一倍。

一帧可能跨过动画结束、等待结束甚至下一动作开始。播放器保留本帧剩余时间，继续推进下一阶段，避免十倍模式每一步额外多等一帧。这能保证计时逻辑准确，但设备帧率仍决定实际能显示多少中间画面。

暂停表示不再启动后续动作，当前动作会完成。按住单步按钮设置连续请求，松开取消请求。它们共享同一队列，因此暂停后接着单步操作不用重新求解。

**后台计算与界面怎样协作**

`ui.py` 接收按钮和鼠标事件，取出颜色快照交给一个后台工作线程。后台只计算解法，不触碰三维实体；主线程在每帧检查任务是否完成，再把步骤列表交给播放器。

整个流程为：鼠标或按钮 → 界面校验与快照 → 求解器动作列表 → 播放器逐步执行 → 模型提交动作 → 显示层同步颜色。

例如只修改按钮位置时，通常只需改 `ui.py`；只修改自动等待规则时，主要改 `playback.py`。这就是高内聚、低耦合在本项目中的具体含义：相关规则集中在负责它的模块里，模块之间用少量明确的数据交换。

**建议动手练习**

1. 先运行 `tests.test_core`，观察动作与逆动作、四次四分之一圈的检查。
2. 在独立练习文件中用固定种子打乱，打印当前状态并交给求解器，再逐步重放。
3. 阅读 `tests/test_playback.py` 的模拟显示器，理解为什么无需打开窗口也能检查动画的时间规则。
4. 最后阅读图形测试，观察如何用实际实体位置和射线命中确认画面与模型一致。

修改约定时先写一个会失败的测试，再改实现。完整命令见 [README](../README.md)，贡献要求见 [CONTRIBUTING](../CONTRIBUTING.md)。
